## Post 2 — How-to / Teardown

### X / Twitter
How today's double-booking checker actually works (no magic):

1. Group jobs by technician
2. Sort each tech's jobs by start time
3. For each pair: does job B start before job A ends + drive buffer?
4. If yes → conflict, flag both, tally the $ at risk

That's the whole engine.

### LinkedIn
Teardown of today's build, the Double-Booking Checker — because "just check the calendar" is easier said than done when you're juggling three techs and a phone that won't stop ringing.

The logic is simple on purpose:

1. **Group by tech.** A conflict only matters within one person's (or one truck's) schedule.
2. **Sort by start time.** You only ever need to compare a job to the one right after it.
3. **Check the gap.** Does the next job start before the current one finishes — plus the drive/reset buffer you set? If yes, that's a conflict.
4. **Tally what's at risk.** Every conflict flags the dollar value of the job that would start late.

On a sample day of 16 jobs across 3 techs, that logic caught 3 conflicts — all cases where a job was booked to start the instant (or before) the previous one wrapped, with no travel time in between. $920 of the day's value was sitting on jobs that would've run late.

The fix isn't complicated. It's just a check most businesses never run, because nobody has time to eyeball a schedule row by row every morning.

## Post 3 — Opinion / Lesson

### X / Twitter
Unpopular opinion: most double-bookings aren't a scheduling problem.

They're a missed-call problem.

Nobody double-books on purpose. It happens when a job gets booked fast, by phone or text, with no live look at the calendar — the same rushed moment that causes a missed call to get ignored.

Fix the intake, fix the calendar.

### LinkedIn
A lesson from building a Double-Booking Checker today: the double-booking isn't really the problem. It's a symptom.

Every conflict I've ever seen on a home-service schedule traces back to the same root cause — a job got booked in a hurry, by whoever picked up the phone or answered the text, without a real-time look at what the crew already had on the board.

That's the exact same failure point that causes a missed call to become a missed job in the first place: intake that isn't actually connected to the calendar. Fast, manual booking either loses the lead entirely (missed call) or books it into a slot that doesn't exist (double-booking). Same root cause, two different symptoms.

The fix isn't "be more careful." It's making sure whoever — or whatever — books the job can actually see the calendar before confirming the time. That's the whole idea behind AnswerCatch: every call gets answered, and every booking gets checked against the real schedule before it's confirmed.

Building tools like today's checker in public because I think most service businesses are bleeding money in small, boring, fixable ways like this — not big dramatic ones.
